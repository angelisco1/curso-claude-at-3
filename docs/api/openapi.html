API de gestión de restaurantes Resttek.

Contrato de la API de Resttek. De momento documenta la gestión de mesas (issue #5), los endpoints de pedidos que usan los frontends en esa funcionalidad y los códigos de descuento aplicables a los pedidos.

Autenticación

Todas las rutas documentadas exigen un JWT en la cabecera Authorization: Bearer <token>, obtenido en POST /api/v1/auth/login. El payload del token contiene id, role y restaurantId del usuario (los clientes se guardan en la misma tabla employees con rol cliente y restaurantId: null).

Formato de errores

  • Errores de dominio (lanzados por los servicios y gestionados por el errorHandler): { "error": "<NombreDelError>", "message": "<detalle>" }.
  • Errores de los middlewares authenticate / authorize / authorizeRestaurant (401 y 403): solo { "error": "<detalle>" }.
  • Los endpoints de pedidos POST /api/v1/orders, GET /api/v1/orders/active y GET /api/v1/orders/{id} gestionan sus errores en el propio controlador y devuelven solo { "error": "<mensaje>" }. Los de descuento de un pedido (/api/v1/orders/{id}/discount) y los de /api/v1/discounts usan el errorHandler.

Códigos de descuento

  • Un descuento es un código (elegido libremente por el admin) con un porcentaje entero entre 1 y 100. Es global: vale para los pedidos de cualquier restaurante.
  • El código se normaliza con trim() + mayúsculas (" black_friday " → BLACK_FRIDAY), debe cumplir ^[A-Z0-9_-]{3,30}$ y es único.
  • Un descuento puede desactivarse (active: false); un código inactivo no se puede aplicar a pedidos, pero los pedidos que ya lo tenían lo conservan.
  • Un pedido admite un único descuento. Al aplicarlo, el pedido guarda una copia del código y del porcentaje (discountCode, discountPercentage), así que editar, desactivar o borrar el descuento después no altera los pedidos existentes.
  • En las lecturas de pedidos se devuelven subtotal (suma de dishPrice × quantity de los ítems), discountAmount (subtotal × porcentaje / 100) y total (subtotal − discountAmount), redondeados a 2 decimales.
  • Importes fijados al aplicar el descuento: al aplicar un código, los tres importes se calculan con los precios de ese momento y se guardan en el pedido. Las lecturas devuelven los importes guardados, así que si después cambia el precio de un plato el total del pedido con descuento no cambia. Al quitar el descuento se borran.
  • Pedidos sin descuento: no tienen importes guardados; se calculan al leer con el precio actual de los platos (discountAmount: 0, total = subtotal). Quedan fijados en cuanto se les aplica un código.
  • Cambios en los ítems: cambiar el estado de un ítem (PATCH .../items/{itemId}/status) no afecta a los importes. La API no permite añadir, quitar ni modificar platos o cantidades de un pedido ya creado, así que el importe fijado no puede quedar desfasado respecto a sus ítems. Si en el futuro se permite, la regla será recalcular los importes fijados con el mismo porcentaje guardado y los precios del momento del cambio.

Acceso por restaurante (mesas)

Los roles de empleado ligados a un restaurante (manager, camarero, cocinero) solo pueden operar sobre las mesas de su restaurante (restaurantId del token igual al restaurantId de la ruta); si no, se responde 403. El admin y el cliente no tienen esa restricción. Las rutas existentes (ingredientes, platos) no hacen esta comprobación; las de mesas sí, mediante un nuevo middleware authorizeRestaurant.

Reservas con dueño (reservedFor)

Una mesa en estado reservada puede tener un cliente dueño de la reserva. Se modela así:

  • Columna tables.reserved_for con el id del cliente (no el email): el id es lo que viaja en el JWT (req.user.id), es estable y es lo mismo que se guarda en orders.client_id.
  • Como los empleados no conocen el id de los clientes, al reservar se indica reservedForEmail en PATCH /{id}/status; la API lo resuelve al id de un usuario con rol cliente (si no existe, 400 InvalidReservationClientError).
  • La respuesta expone reservedForClientId y reservedForEmail (ambos null si la mesa no está reservada o la reserva no tiene dueño).
  • Al cambiar la mesa a cualquier estado distinto de reservada (incluida la ocupación), la reserva se limpia (reserved_for = NULL).
  • GET /available devuelve las mesas libre, las reservada cuyo dueño es el usuario autenticado y las ocupada por él mismo, siempre con capacidad suficiente.
  • POST /{id}/occupy (solo cliente y admin) ocupa de forma atómica una mesa libre, reservada para el propio usuario u ocupada ya por él (idempotente), con un único UPDATE ... WHERE condicional.
  • Un cliente nunca recibe datos de reservas de otras personas: no puede usar GET / ni GET /{id} (403), GET /available solo devuelve sus propias reservas y ocupaciones, y occupy devuelve la mesa con la reserva ya limpia.
  • El dueño de la reserva es opcional: una reserva sin reservedForEmail (p. ej. reserva telefónica) no la puede ocupar ningún cliente con occupy; solo la cambian los empleados.
  • La reserva es un estado simple, sin fecha ni hora.
  • En GET /available cada mesa trae reservedForMe (true si está reservada para el usuario) y occupiedByMe (true si ya la ocupa el usuario).

Ocupante (occupiedBy)

  • Columna tables.occupied_by con el id del cliente que ocupó la mesa con occupy.
  • Es null si la mesa la puso ocupada un empleado con PATCH /{id}/status.
  • Se limpia al cambiar la mesa a cualquier otro estado.
  • Permite que occupy sea idempotente para el mismo cliente (doble clic o reintento).

Estado de la mesa

El estado solo se cambia con PATCH /{id}/status; POST y PUT no aceptan status. Las mesas se crean siempre libre.

Liberación de mesas

La liberación es siempre manual: un empleado (admin, manager o camarero) cambia el estado a libre. Si el cliente abandona tras ocupar, la mesa sigue ocupada hasta entonces. Liberar está permitido aunque la mesa tenga pedidos activos.

Mesas de otro restaurante

Una mesa que existe pero pertenece a otro restaurante se trata como inexistente (404 TableNotFoundError), y los listados de un restaurante sin mesas (o inexistente) devuelven []. Solo createTable comprueba que el restaurante existe (404 RestaurantNotFoundError).

Limitaciones conocidas (fuera del alcance de la issue #5)

  • POST /api/v1/orders no valida tableId: no comprueba que la mesa exista, sea del restaurante, esté ocupada ni que la ocupe el cliente que hace el pedido.
  • GET /api/v1/orders/active no tiene control de rol ni de restaurante: cualquier usuario autenticado, incluido un cliente, puede listar los pedidos activos de cualquier restaurante.

Ocupar una mesa

Pone la mesa en ocupada con occupiedByClientId = usuario autenticado, de forma atómica con un único UPDATE condicional:

UPDATE tables SET status = 'ocupada', occupied_by = :userId, reserved_for = NULL, updated_at = :now
WHERE id = :id AND restaurant_id = :restaurantId AND capacity >= :people
  AND (status = 'libre'
       OR (status = 'reservada' AND reserved_for = :userId)
       OR (status = 'ocupada' AND occupied_by = :userId))
  • Es idempotente para el mismo usuario: si la mesa ya está ocupada por él (doble clic o reintento), responde 200 con la mesa.
  • Si no se aplica: 404 TableNotFoundError si la mesa no existe o es de otro restaurante; en otro caso 409 TableNotAvailableError (ocupada por otra persona o por un empleado, reservada para otra persona o sin dueño, o capacity < people) y no cambia nada.
  • La respuesta solo contiene datos del propio usuario (la reserva queda limpia).

Los empleados no usan este endpoint: sientan a los clientes con PATCH /{id}/status.

Roles: cliente y admin (este último, para pruebas). El resto recibe 403.

Efectos sobre la reserva y el ocupante (siempre se reescriben):

Nuevo estado reservedFor* occupiedByClientId
libre null null
ocupada null null (la sienta un empleado)
reservada cliente de reservedForEmail, o null (reserva sin dueño) null

reservedForEmail solo se tiene en cuenta con status: reservada y debe ser el email de un usuario con rol cliente (si no, 400 InvalidReservationClientError); con otro estado se ignora.

Roles: admin, manager, camarero (manager y camarero, solo de su restaurante). El cocinero y el cliente reciben 403.

Crear un pedido

Crea un pedido con estado pendiente en todos sus ítems. El clientId se toma del id del JWT. Cada ítem con quantity N se desglosa en N ítems de quantity: 1 (cada uno con su estado propio).

tableId es opcional y nullable y no se valida (ver "Limitaciones conocidas"): el cliente envía el id de la mesa que ocupó con occupy. La respuesta incluye tableId tal cual se guardó (no incluye el número de mesa).

Los errores los gestiona el propio controlador: cualquier error de validación (o de la base de datos, p. ej. restaurante inexistente) responde 400 con { error: <mensaje> }.

Roles: cualquier usuario autenticado (no hay authorize).

Aplicar un código de descuento a un pedido

Aplica al pedido el descuento cuyo código se indica. El código se normaliza (trim() + mayúsculas) antes de buscarlo, así que " discount30 " equivale a DISCOUNT30.

  • Un pedido admite un único descuento: si ya tiene otro código distinto responde 409 OrderDiscountAlreadyAppliedError (hay que quitarlo antes con DELETE).
  • Es idempotente: volver a aplicar el mismo código devuelve 200 sin cambios.
  • El código debe existir (404 DiscountNotFoundError) y estar activo (409 DiscountInactiveError).
  • El pedido guarda una copia del código y el porcentaje, y fija subtotal, discountAmount y total calculados con los precios de los platos en este momento. Las lecturas posteriores devuelven esos importes aunque cambien los precios.
  • Al reaplicar el mismo código (idempotente) los importes fijados no se recalculan.

Devuelve el pedido completo, con los importes fijados.
